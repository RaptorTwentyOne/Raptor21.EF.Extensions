# Sample: one table, one result shape, five procedures, two migrations

A console app that shows the whole loop this library exists for.

| File | What it demonstrates |
|---|---|
| `Data/Product.cs`, `Data/CatalogDbContext.cs` | Tables the ordinary EF way, plus one `RegisterStoredProcedures` call that puts the `.sql` files on the model |
| `Data/ProductListResult.cs` | A keyless entity — a result shape rather than a table, declared with `HasNoKey().ToView(...)`, which is what a row type binds to |
| `Data/CatalogDbContextFactory.cs` | The differ replacement, shared by `dotnet ef` and the app — design time and run time must agree or migrations quietly lose the procedures |
| `DbScripts/*.sql` | The procedure bodies. Source of truth, embedded in the assembly, read by both the migration and the startup applier |
| `Catalog/CatalogProcedures.cs` | Five declarations, no bodies: RETURN value + OUTPUT parameter, result set, result set + RETURN, model-bound result set, and plain non-query |
| `Catalog/ProductRow.cs` | A hand-written positional `[SqlRow]` record; the generator writes its `FromDataRecord` |
| `Catalog/ProductListRow.cs` | `[SqlRow(Entity = typeof(ProductListResult))]` — the members come from the model, so the generator writes the primary constructor too |
| `Migrations/` | Generated by `dotnet ef migrations add` — `CreateTable` and four `CREATE OR ALTER` in the first `Up`, one more in the second |
| `Program.cs` | Migrate, validate every contract against the live schema, call the procedures, then call them again on a connection and transaction the program owns and roll it back |
| `Data/BorrowedConnectionProvider.cs` | The whole of what borrowing takes: one `LeaseAsync` override returning `SqlConnectionLease.Borrow`, so a generated call joins a transaction it did not begin |

## The two ways to say what a row is

Both compile side by side in this sample, on purpose, and neither is going away. They are two answers
to one question — who says what the shape is. `ProductRow`: this C# file does. `ProductListRow`: the
model does, and the developer says which entity.

`ProductRow` spells its members out. Reach for that whenever the shape is the procedure's own: a
projection or an aggregate no entity type describes, a column that needs a `[SqlColumn]` rename, a
member order chosen to match a `SELECT` that already exists, an entity whose columns are not
exclusively its own (table splitting, an inheritance hierarchy, an owned type), or a value-converted
property whose stored type the generator cannot convert.

`ProductListRow` names an entity type instead, and the generator reads the checked-in
`Migrations/CatalogDbContextModelSnapshot.cs` as ordinary C# syntax in the same compilation — no EF
types, no database connection, no reflection, no `SELECT` parsing. Four member names, four .NET types,
four column names and four nullability decisions stop being a second copy of the model that goes
quietly wrong the day a column changes. Three things come with that:

- **Member order is the model's** — primary key first, then alphabetical — and the procedure's `SELECT`
  must match it, because result columns are validated positionally. `ProductRow` is the illustration:
  its order is `Id, Sku, Name, Price, UpdatedUtc`, while the model's order for `Product` is
  `Id, Name, Price, Sku, UpdatedUtc`.
- **The member type is the model's stored type**, not the entity class's. A value-converted or enum
  property is refused at build time rather than emitted under the other type's name.
- **Shadow properties are skipped silently**, so a shadow foreign key the model knows about must not
  appear in the `SELECT` either.

The row type and the snapshot have to be in one compilation. A snapshot in a referenced assembly
carries no syntax at all, only IL, so a source generator cannot read it.

## Running it

Needs SQL Server. Without `SAMPLE_SQL_CONNECTION` it falls back to LocalDB.

```bash
export SAMPLE_SQL_CONNECTION="Server=localhost;Database=Raptor21EfExtensionsSample;User Id=sa;Password=...;TrustServerCertificate=True"
dotnet run --project samples/Raptor21.EF.Extensions.Sample
```

## Trying a change

Edit any file under `DbScripts/`, then:

```bash
dotnet ef migrations add TweakUpsert --project samples/Raptor21.EF.Extensions.Sample
```

The new migration contains one `CREATE OR ALTER` — just the procedure you touched. That is the point:
the procedure body is in the repository, in the migration history, and in code review, instead of being
whatever the last person to open SSMS left behind.

Change the model instead — add a property to `ProductListResult` — and the same command rewrites the
snapshot, which is the generator's input: `ProductListRow` grows a member on the next build, because it
is bound to that entity with `[SqlRow(Entity = ...)]`. Nothing reads the `SELECT` list, so keeping
`Product_ListView.sql` in step with the model is yours to do; the startup validator is what catches it
if you do not.

## Why the project file spells out two references

The sample builds from source, so it wires the runtime and the generator by `ProjectReference`. A real
consumer writes one `PackageReference` to `Raptor21.EF.Extensions.StoredProcedures` and gets both,
because the generator is packed inside that package under `analyzers/dotnet/cs`.
